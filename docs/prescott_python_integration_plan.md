# План объединения ветвящейся MRG-модели и ephaptic coupling Prescott в Python

## Цель
Собрать **единую Python/NEURON модель**, где:
- есть ваш аксон с ветвлениями (`MRGaxon` в `Main_model/MRG_model/Sensory_axon`),
- рядом размещены дополнительные аксоны (соседи),
- взаимодействие между аксонами реализуется через внеклеточную среду (эфаптическая связь),
- можно измерять: как эфаптическая связь влияет на проведение через точки ветвления.

---

## Почему это реалистично сделать
Обе модели уже опираются на одну и ту же физику/инфраструктуру:
1. На MRG-подобные секции (`node`, `MYSA`, `FLUT`, `STIN`).
2. На механизм `extracellular` в NEURON.
3. На нодальные каналы в `.mod` (в Prescott это `AXNODE.mod`, в вашей модели — `newaxnode/axnode`).

То есть задача не «писать всё с нуля», а **перенести preprocessing и схему связей Prescott в Python** и подключить это к вашему `MRGaxon`.

---

## Ключевая идея объединения

### 1) Оставить вашу Python-модель как ядро
Использовать текущий `MRGaxon` как базовый класс одиночного аксона (он уже строит ветвления и умеет запускать серии симуляций).

### 2) Добавить «пучок» аксонов как новый уровень
Создать новый класс-обёртку, например:
- `EphapticBundleModel`

Он будет хранить:
- один «главный» ветвящийся аксон,
- N соседних аксонов (обычно без ветвлений на первом этапе),
- матрицы внеклеточных связей между соответствующими секциями.

### 3) Перенести `Main_Code.m` в Python
В Prescott `Main_Code.m` делает preprocessing:
- геометрия поперечного сечения (`R`, `C`, расстояния),
- соседство и «кто с кем связан»,
- соответствия секций вдоль оси,
- коэффициенты/длины для межаксонных и boundary-связей.

Это переписывается в Python модуль, например:
- `python_model/ephaptic_geometry.py`

### 4) Реализовать boundary-кабель в Python/NEURON
Логику `Boundarycable.hoc` лучше реализовать классом Python, который создаёт цепь секций с `extracellular`.

### 5) Связь по внеклеточному потенциалу
Вместо генерации множества txt/mat-файлов делать всё в памяти Python:
- подготовить таблицу пар сегментов, где есть эфаптическая связь,
- на каждом шаге интегрирования пересчитывать/обновлять вклад в `e_extracellular` (или эквивалентный механизм через point-process/LinearMechanism в зависимости от устойчивости схемы).

## Предложенная архитектура (Python)

```text
python_model/
  ephaptic/
    __init__.py
    geometry.py          # перенос Main_Code.m: R/C/dist/neighboring/connect maps
    boundary.py          # перенос Boundarycable.hoc
    fiber_factory.py     # создание MRG-аксонов (в т.ч. ветвящихся)
    coupling.py          # матрица ephaptic-связи и её применение в NEURON
    stimuli.py           # общий интерфейс стимуляции (главный + соседи)
    metrics.py           # CV, блоки проведения, spike transfer у branch points
    experiments.py       # сценарии запусков
```

## Пошаговая миграция Prescott → Python

### Этап A. Геометрия и preprocessing (без динамики)
1. Переписать вычисления из `Main_Code.m` в NumPy:
   - `Distance_Centers`, `Distance_edge`, `neighboring`.
2. Убрать `eval` и строки с именами секций — заменить на структурированные индексы (`dataclass` + словари).
3. Сравнить с оригиналом на 2–3 кейсах (`edge dist = 0.1/1/3`).

**Результат:** Python-функция возвращает полностью готовую структуру связей.

### Этап B. Конструктор аксонов
1. Создать фабрику аксонов (единый API):
   - `build_branching_fiber(...)`
   - `build_straight_fiber(...)`
2. Привести типы секций к единому именованию (`node/mysa/flut/stin`).
3. Проверить, что одиночные аксоны дают сопоставимые AP/CV с текущей моделью.

### Этап C. Boundary и ephaptic-матрица
1. Python-версия `Boundarycable`.
2. Сборка разреженной матрицы проводимостей/сопротивлений между сегментами.
3. Тест в пассивном режиме: инъекция в одном волокне → разумный `vext` в соседях.

### Этап D. Полная динамика
1. Подключить нодальные механизмы (`newaxnode` или `axnode`) для всех волокон.
2. Запускать сценарии:
   - стимуляция только главного волокна,
   - стимуляция главного + фон у соседей,
   - sweep по расстояниям/числу соседей/позиции ветвления.

### Этап E. Метрики ветвления под ephaptic влиянием
Рекомендую сразу считать:
- вероятность прохождения AP через branch point,
- задержку AP до/после ветвления,
- коэффициент передачи в дочернюю ветвь,
- случаи block/failure, зависящие от фазового сдвига соседей.

## Минимальный MVP (что сделать первым)

**MVP-1 (2–3 недели):**
- 1 ветвящийся аксон + 2 прямых соседних,
- фиксированная геометрия (без автопэкинга),
- одна частота стимуляции,
- сравнение «с ephaptic / без ephaptic» по spike transfer в branch point.

**MVP-2:**
- sweep по расстоянию между волокнами,
- sweep по частоте/амплитуде,
- графики зоны «безопасного проведения» через ветвление.

---

## Что лучше не переносить «как есть» из Prescott
1. `eval`-ориентированную генерацию имён секций.
2. Файло-ориентированный обмен (`txt/mat`) между этапами.
3. Смешение preprocessing и симуляции в одном скрипте.

Лучше: чистые Python-функции + сериализация в `h5`/`json` при необходимости.

---

## Риски и как их снизить
1. **Численная жёсткость/скорость** при большом числе аксонов.
   - Сначала малые сети (3–5 волокон),
   - разреженные матрицы (`scipy.sparse`),
   - профилирование.

2. **Несоответствие старым результатам Prescott.**
   - Ввести regression-тесты на базовых кейсах (пики V, задержки, CV).

3. **Сложность калибровки boundary.**
   - Сделать boundary опциональным режимом (`none`, `grounded`, `finite_cable`).

## Практический старт в вашем репозитории
1. Добавить пакет `python_model/ephaptic/`.
2. Вынести из `MRG_lib.py` общий интерфейс доступа к ключевым сегментам (node index → segment handle).
3. Добавить сценарий `python_model/run_ephaptic_branching_experiment.py`.
4. Логировать результаты в тот же HDF5-формат, чтобы анализ не ломался.

## Итог
Да, модели **можно и логично** совместить. Лучший путь — не копировать Prescott 1-в-1, а перенести его как:
- Python preprocessing геометрии,
- Python сборку boundary и матрицы ephaptic-связей,
- запуск в вашем текущем NEURON-пайплайне с ветвящимся аксоном.

Если хотите, следующим шагом могу предложить **конкретный skeleton кода (классы + сигнатуры функций)** и **план проверки валидности по шагам**, чтобы можно было сразу начать реализацию.
